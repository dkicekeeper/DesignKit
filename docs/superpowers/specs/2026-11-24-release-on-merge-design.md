# Номер релиза при слиянии: заметки в PR, релиз делает бот

Дизайн, 2026-11-24. Решение владельца: номер версии получает не PR, а слияние в `main`; бот
может коммитить в `main`; открытые сейчас PR (#105, #109, #110, #111) сливаются по старой схеме,
новая включается после них.

## Зачем

Несколько сессий Claude параллельно открывают релизные PR в DesignKit. Сейчас каждый PR сам
выбирает номер (`VERSION`, верхний раздел CHANGELOG.md, `since:` на страницах Gallery,
упоминания «(8.15.0)» в доках и комментариях), и от этого:

- **номера сталкиваются и устаревают**: «бронь» — это договорённость «посмотри открытые PR»;
  #105 до сих пор несёт 8.13.0, который `main` уже занял; мой #111 пришлось перенумеровать;
- **перенумерация ручная и большая**: в #109 номер стоит в 59 добавленных строках, в #105 — в 24;
- **конфликты гарантированы**: `VERSION` и верх CHANGELOG.md конфликтуют у любых двух
  параллельных PR, сгенерированный docs/components.md(.json) — у любых двух, что трогают
  страницы Gallery;
- **порядок тегов не защищён**: `release.yml` ставит тег на любой непомеченный `VERSION` в
  `main`, даже меньше последнего; приложения берут самый старший тег (`sort -V` в их
  `designkit.yml`), так что релиз не по порядку до них не доходит.

Успех: сессия открывает PR, не думая о номере; PR никогда не конфликтует с другими из-за
релизных файлов; каждое слияние с заметкой даёт следующий по порядку тег, GitHub Release и
сборку Gallery в TestFlight с правильной версией.

## Цели

- PR не содержит номера своей версии: он объявляет тип изменения и текст релиза.
- Слияние PR с заметкой в `main` → ровно один релиз: следующий номер, раздел CHANGELOG.md,
  `VERSION`, тег `X.Y.Z`, GitHub Release, TestFlight.
- Номера всегда растут; два слияния подряд дают два релиза по порядку слияния (или один общий,
  см. «Несколько заметок сразу»).
- `VERSION`, CHANGELOG.md и docs/components.md(.json) в PR не правятся, поэтому не конфликтуют.
- Для приложений ничего не меняется: теги `X.Y.Z`, заметки релиза, их update-workflow.
- Экран Updates в Gallery и `ChangelogTests` работают как раньше (CHANGELOG.md того же формата).

## Не цели

- Пакетные релизы по кнопке или по расписанию (вариант C): можно включить позже на тех же
  заметках.
- Изменения в update-workflow приложений.
- Перевод открытых #105, #109, #110, #111 на заметки: они сливаются по старой схеме до
  переключения.
- Автослияние, merge queue.

## Анти-цели (провал, даже если «работает»)

- Тег меньше или равный уже существующему.
- После релиза в `main` остаётся метка `vNext` (или она заменилась номером чужого релиза).
- Слияние с заметкой прошло, а релиза нет, и никто об этом не узнал.
- Бот затирает чужой коммит в `main`.

## Ограничения

- Бот пушит стандартным `GITHUB_TOKEN`: его коммит **не запускает** другие workflow (CI,
  TestFlight). Исключение — `workflow_dispatch`, его этот токен запускать может (нужно
  `permissions: actions: write`).
- Защита `main` не мешает боту (подтверждено владельцем).
- `concurrency` в GitHub держит один выполняющийся и **один** ожидающий запуск: третий быстрый
  запуск отменяет ожидающий второй. Логика не должна зависеть от того, что каждый запуск
  дойдёт до конца.
- Формат CHANGELOG.md, проверка `changelog.py check`, парсер экрана Updates
  (`Gallery/Gallery/Updates/Changelog.swift`) и `ChangelogTests` остаются совместимыми.
- Сессии работают в Linux-контейнере без Swift: всё, что проверяет PR, — Python в CI.

## Варианты (выбран A)

- **A. Заметка в каждом PR и бот при слиянии** — выбран владельцем. PR кладёт
  `.changes/<имя>.md` с типом изменения и текстом; где раньше писал номер, пишет `vNext`. Бот
  после слияния считает номер, собирает раздел CHANGELOG.md, пишет `VERSION`, заменяет `vNext`,
  пересобирает справочник компонентов, коммитит, ставит тег. Разные файлы заметок → нет
  конфликтов; номер считается в одном месте → нет столкновений и неверного порядка.
- **B. Раздел «Unreleased» в CHANGELOG.md и метка на PR** (схема Keep a Changelog) — отвергнут:
  все PR правят один раздел, конфликты остаются; метка живёт вне git.
- **C. Заметки копятся, релиз по кнопке или раз в день** — отложен: меньше тегов, но
  исправления ждут, и кто-то должен нажимать «Release». Сейчас релиз на каждый PR.

## Как устроено

### Заметка (`.changes/<имя>.md`)

Один файл на PR. Имя должно быть уникальным: ветки сессий переиспользуются под новые PR
(#104 и #106, #95–#98), и одинаковое имя дало бы конфликт «изменён / удалён». Поэтому имя —
ветка без `claude/` плюс дата и короткая тема, например `optimistic-bell-2026-11-24-numbers.md`.
Формат:

```markdown
---
bump: minor
---
Одна-две строки о том, что это за релиз (как вступление раздела CHANGELOG сейчас).

### Added
- …

### Gallery and tooling
- …
```

- `bump`: `patch`, `minor` или `major` (правила semver из CLAUDE.md: новое API — minor, удаление —
  только major).
- Разделы и правила те же, что у раздела CHANGELOG.md сейчас: порядок `Added`, `Changed`,
  `Deprecated`, `Removed`, `Fixed`, `Migration`, `Gallery and tooling`; английский; без тире
  «—», без эмодзи; один уровень `- `.
- Ссылку на PR писать не нужно: её добавляет бот.
- PR без заметки — не релиз (правка доков, CI). Таким и остаётся. Если он меняет `Sources/` или
  `Gallery/`, проверка предупреждает, но не падает (#94 и #106 так и шли, без релиза).
- Содержание и тип должны сходиться: `### Added` при `bump: patch` и `### Removed` без
  `bump: major` — ошибка. Ни один из 94 разделов CHANGELOG.md это правило не нарушает.

### Метка `vNext`

Где PR раньше писал номер своей версии, он пишет `vNext`: `since: "vNext"` на странице Gallery,
«(vNext)» в design-system.md и комментариях, `@available(*, deprecated, message: "… vNext …")`.

Правило замены (моё предложение): **`vNext` без обратных кавычек — метка, бот её заменяет;
`` `vNext` `` в обратных кавычках — само слово, остаётся.** Так документация о механизме
(CLAUDE.md, docs/releasing.md) может называть метку, не теряя её при релизе. В Swift-строках
кавычки двойные, так что `since: "vNext"` заменяется.

Замена идёт по всем отслеживаемым текстовым файлам, кроме `.changes/` (их бот удаляет),
бинарных (PNG снапшотов), скрипта бота и его тестов, этого документа и `.github/workflows/`:
`GITHUB_TOKEN` не может пушить изменения файлов workflow, такой push был бы отклонён.

### Мажорный релиз: номер явно

У мажора номер стоит и в именах файлов (`docs/migration-9.0.md`, `scripts/migrations/9.0.0.json`,
из имени которого `migrate.py` берёт номер), и в форме «X.0» (`TODO(DesignKit 9.0)`, строка
«Moving an app to 9.0» в CLAUDE.md, ссылки в разделе Migration). Метка `vNext` этого не
покрывает. Решение владельца: **заметка мажора несёт номер явно**, `version: 9.0.0` (поле
разрешено только при `bump: major`), и PR пишет этот номер в файлах и тексте, как сейчас.

- Номер мажора зависит только от предыдущего мажора: минорные и патч-релизы, слитые, пока PR
  открыт, его не меняют (8.0.0 вышел так после 7.1.0).
- Бот считает номер как обычно и сверяет с `version:`; расхождение — ошибка запуска (шаг 6),
  ничего не коммитится, в PR комментарий.
- Проверка в PR: `version:` есть ровно у `bump: major`, это `X+1.0.0` от старшего из последнего
  тега и `VERSION` основания; меток `vNext` у мажора может не быть.
- Два мажора одновременно не открывают: второй ждёт слияния первого (решает владелец).

### Бот (`release.yml` → `.github/scripts/release.py`)

Запускается на каждый push в `main` (и вручную), `concurrency: release`, без отмены
выполняющегося. Шаги:

1. Взять свежий `main` (`fetch` + `reset` на `origin/main`), а не коммит, на котором запуск
   стартовал: так запуск после отменённого соседа подберёт и его заметки.
2. Сначала долги: если `VERSION` в `main` без тега (запуск до этого упал после коммита, или
   переходный случай со старой схемой), поставить тег и Release на нём, как сейчас. Если заметок
   нет → только шаг 7 (справочник) и выход.
3. Номер: база = старший из (последний тег `X.Y.Z` по `sort -V`, `VERSION`); тип = самый
   старший `bump` из заметок; `patch` → Z+1, `minor` → Y+1.0, `major` → X+1.0.0 (и он должен
   совпасть с `version:` заметки мажора). Проверка: новый номер больше последнего тега, иначе
   ошибка.
4. Раздел CHANGELOG.md: `## X.Y.Z - <дата>`, вступление(я), ссылка(и) на PR, затем разделы
   заметок. Дата — сегодняшняя по UTC, но не раньше даты верхнего раздела (проверка порядка дат
   в `changelog.py`). PR — по коммиту, который добавил заметку (`git log --diff-filter=A`), из
   сообщения merge-коммита «Merge pull request #N» или через `gh`; если не нашёлся — без ссылки.
5. `VERSION` = номер; замена `vNext` (правило выше); удалить заметки.
6. Проверки до коммита: `changelog.py check` проходит; меток `vNext` (без кавычек) не осталось.
7. Пересобрать docs/components.md и .json (`components_reference.py write`).
8. Если что-то изменилось — коммит «Release X.Y.Z» (или «docs: regenerate the component
   reference», если релиза нет) от `github-actions[bot]`, push в `main`. Push отклонён (кто-то
   слил PR между шагами) → повторить с шага 1 (до 3 раз): свежая заметка тогда войдёт в этот же
   релиз, а ожидающий запуск найдёт пустую `.changes/`.
9. Тег `X.Y.Z` на коммит бота, GitHub Release с текстом раздела (как сейчас).
10. `gh workflow run testflight.yml --ref X.Y.Z` — на тег релиза, а не на `main`, чтобы сборка
    была ровно этим коммитом, даже если за ним уже слили следующий PR.
11. Если что-то упало: запуск красный, и бот пишет комментарий в PR, чья заметка не вышла
    (что упало и как перезапустить `release.yml` вручную).

### Несколько заметок сразу

Обычно в `main` одна заметка (одно слияние — один запуск). Если запуск застал несколько
(быстрые слияния, отменённый ожидающий запуск, повтор после отклонённого push), он делает
**один** релиз из всех: тип — старший, вступления подряд, пункты каждого раздела подряд в
порядке слияния, ссылки на все PR. Причина: код всех этих PR уже в одном коммите, и тег на нём —
честно один релиз; разнести их по разным тегам нельзя без переписывания истории `main`.

### TestFlight

- На push слияния, где в `.changes/` есть заметки, сборка пропускается (preflight): за ним
  придёт релиз бота, а версия в этот момент ещё старая.
- Сборку релиза запускает бот (шаг 10). «What to Test» берёт раздел версии, если на `HEAD` стоит
  тег, равный `VERSION` (сейчас проверка «этот push изменил `VERSION`»; при запуске вручную на
  коммите бота она тоже сработает, но тег надёжнее).
- Push без заметок (не релиз) собирается как сейчас.

### Справочник компонентов

docs/components.md и .json пишет только бот (шаг 7), после каждого push в `main`. PR их не
коммитит, поэтому не конфликтует из-за них. CI и в PR, и на `main` проверяет только, что
генератор отрабатывает без ошибок: проверка свежести падала бы после каждого слияния, пока бот
не допишет файл. Приложения читают справочник по своему тегу — тег стоит
на коммите бота, где файл свежий.

### Проверки в PR (`changelog.py check --base <merge-base с main>`)

К тому, что проверяется сейчас, добавляется сравнение с основанием:

- `VERSION` не изменён, в CHANGELOG.md не добавлено разделов `## X.Y.Z` (это делает бот);
- каждая заметка, которую ветка добавляет или меняет, разбирается: `bump` из трёх значений,
  разделы и правила текста, тип сходится с разделами;
- если ветка добавляет `vNext` без кавычек, в ней должна быть заметка (иначе метка доживёт до
  чужого релиза и получит не тот номер);
- docs/components.md и .json не изменены веткой (их пишет бот) — предупреждение или ошибка,
  решает строитель (см. ниже).

На `main` проверка остаётся как сейчас (формат, `VERSION` = верхний раздел).

### Документация

- Новый docs/releasing.md: заметка, метка, что делает бот, как восстановить (ручной запуск
  `release.yml`, что делать с упавшим запуском).
- CLAUDE.md: «Cutting a release» и правила раздела CHANGELOG → заметка; чек-лист переноса
  компонента (п. 4: `components_reference.py write` больше не нужен; п. 6: «under Added in the
  release's CHANGELOG section» → в заметке); «since» на странице Gallery — `vNext`.
- docs/testflight.md, docs/gallery-structure.md (справочник пишет бот), docs/snapshots.md, если
  касается.

## Переход

1. Сливаются #105 (его сессии сначала перенумеровать 8.13.0), #109, #110, #111 — по старой схеме,
   в порядке номеров.
2. PR с механизмом сливается последним. Он сам несёт заметку (`bump: patch`): новый
   `release.yml` из этого же слияния делает его релиз — первая проверка в бою.
3. PR, открытые по старой схеме после переключения, падают на проверке «`VERSION` не изменён» и
   переводятся на заметку (вернуть `VERSION` и CHANGELOG.md, номер → `vNext`).

## Решено владельцем

- Номер при слиянии, вариант A.
- Мажор указывает номер явно (`version:` в заметке), бот сверяет; два мажора разом не открывают.
- Бот коммитит в `main`.
- Открытые PR сливаются по старой схеме, переключение после них.

## Мои решения (можно поправить)

- Метка `vNext`; в обратных кавычках — слово, без них — метка. Замена не трогает скрипт бота,
  его тесты, этот документ и `.github/workflows/`.
- Имя заметки уникально: ветка + дата + тема.
- Код без заметки — предупреждение; тип и разделы заметки должны сходиться.
- Бот сначала помечает оставшийся без тега `VERSION`, TestFlight запускает на тег, о сбое пишет
  в PR.
- Один релиз на запуск из всех застигнутых заметок.
- Дата по UTC, не раньше верхнего раздела; ссылка на PR — ботом.
- Справочник компонентов пишет только бот.
- TestFlight релиза запускает бот через `workflow_dispatch`, сборка на слиянии с заметкой
  пропускается.

## Оставлено строителю

- Устройство `release.py` (отдельный скрипт или подкоманды `changelog.py`), тесты к нему
  (`scripts/test_release.py` или рядом, запуск в задаче CI `Changelog`).
- Как именно искать номер PR (сообщение merge-коммита или `gh`).
- Ошибка или предупреждение, если PR всё же правит docs/components.md.
- Точная проверка «релизной сборки» в testflight.yml (тег на `HEAD`).
